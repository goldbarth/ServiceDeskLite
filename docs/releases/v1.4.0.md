# ServiceDeskLite v1.4.0 — Auto-Routing, Streaming Summaries & AI Insights

### Summary

ServiceDeskLite 1.4.0 turns the assistant from something you talk to into something that works alongside you (roadmap milestone M6).
An incoming ticket is triaged on arrival — category, priority, assignee, and status — and when the classifier is unsure it says so instead of guessing.
A ticket's history collapses into a live, structured summary that streams token by token into its own tab.
And a new AI Insights page reports what the assistant actually did: how much of the work it automated, how often its duplicate check found something, how confident retrieval was, which tools it called, and what it all cost in tokens.
Nothing here loosens the earlier stance: the model still reaches the domain only through the same command handlers as the UI and the API, every change is audited, and a number the system cannot measure is reported as unknown rather than as zero.

### Highlights

- AI auto-routing: a deterministic, rule-based `ITicketRouter` classifies a ticket into category, priority, assignee, and status; a `route_ticket` tool applies the decision through the existing update/assign/change-status handlers, and a confidence gate turns an uncertain decision into a suggestion instead of a silent write (ADR 0032)
- `TicketCategory` becomes a real domain field, with `Uncategorized` distinct from a ticket deliberately routed to `Other`
- Streaming ticket summaries: `GET /api/v1/tickets/{id}/summary` streams summary, next steps, risks, and missing information into the ticket's `AI Summary` tab, token by token; whatever the ticket does not say lands in *missing information* rather than being invented (ADR 0033)
- AI operations dashboard: `GET /api/v1/dashboard/ai` and an `AI Insights` page report automation rate, duplicate-check hit rate, retrieval confidence, per-tool call statistics, and token usage over a trailing seven days (ADR 0034)
- Assistant metrics are persisted behind a port, on both providers; the sink writes on its own DbContext and swallows its own failures, so telemetry can never fail the chat turn it is measuring
- Every rate is nullable to the wire and renders as `n/a`: a system nobody has used has not achieved 0 % automation, and unconfigured semantic search makes confidence unmeasurable rather than low
- New assistant tool `route_ticket` (eleven tools total)

### Demo Notes

#### Suggested demo flow

1. Start the app with `ANTHROPIC_API_KEY`; add `Voyage:ApiKey` and PostgreSQL for the full retrieval path
2. Describe an incident in the Assistant ("the printer on the third floor is dead, several colleagues affected") — watch the chain run: duplicate check, create, route
3. Open the created ticket: category and priority are filled in, an agent is assigned, the status has moved to `Triaged`, and the audit history shows each step with actor `ai-assistant`
4. Describe something vague and watch routing decline to apply itself — the decision comes back as a suggestion with its rationale
5. Open the `AI Summary` tab on a ticket with some history: the four sections fill as the text arrives, and what the ticket never stated shows up under *missing information*
6. Open `AI Insights`: after that one conversation the automation rate, the duplicate-check outcome, the tool table, and the token cost are all populated
7. Reload `AI Insights` on a freshly started API and watch every rate read `n/a` instead of `0 %`

#### What to pay attention to

- Routing never writes to the domain directly; it goes through `UpdateTicketHandler`, `AssignTicketHandler`, and `ChangeTicketStatusHandler`, so validation, the closed-ticket rule, and the audit trail all apply unchanged
- An invalid status transition is skipped, not fatal — the rest of the routing decision still lands
- The summary is a read, not an action: a separate endpoint with no tools, deliberately outside the agentic loop
- Summary section markers (`<<NEXT_STEPS>>`) do not arrive whole in the token stream; the parser holds back any viable marker prefix, so no fragment ever reaches the UI
- The automation rate needs no new bookkeeping: the assistant is audited like every other actor, and `Actor` is the whole difference between an automated action and a human one
- `check_grounding` is kept out of the retrieval confidence average — it grades an answer, not evidence, and blending the two would produce a number that measures nothing

### Included scope

- AI auto-routing: `KeywordTicketRouter`, `RouteTicketHandler` with a confidence gate, `route_ticket` tool, `TicketCategory` domain field, category surfaced in the ticket list and details — #159
- Streaming ticket summaries: marker-delimited model output parsed back into sections, SSE `delta` events tagged by section, `AI Summary` tab — #160
- AI operations dashboard: `IAssistantMetricsSink` + `IAiDashboardRepository` on both providers, `GET /api/v1/dashboard/ai`, `AI Insights` page, `AuditActors.AiAssistant` — #161

### Known limitations

- Not intended for production use
- Still no real auth — the roster is seeded fictitious accounts, not authenticated identities
- Routing is a keyword classifier, deliberately: it is always available and reproducible. An embedding or LLM classifier can sit behind the same port later, and the confidence threshold is hand-tuned
- Summaries are not persisted. They reflect the ticket at read time and are cached only for the lifetime of the page; there is no rate limiting, so reloading the tab costs a model call each time
- Assistant metrics are never pruned. On PostgreSQL the two tables grow with usage; on the InMemory provider they reset with the process
- Retrieval confidence requires PostgreSQL + a Voyage key. Without them the dashboard reports it as unmeasurable rather than low, and the duplicate rate still works from keyword-only matches
- Seeded demo tickets carry no audit events, so a fresh deployment shows a large ticket volume next to zero audited actions
- A model turn the client abandons mid-stream is not counted in token usage
