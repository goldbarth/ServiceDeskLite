# ServiceDeskLite v1.5.0 — Agent Sandbox, Evaluation Suite & Observability

### Summary

Earlier releases grew what the assistant can do; 1.5.0 makes it fit to operate (roadmap milestone M7).
The agent is fenced in — every tool call passes a guard pipeline before it reaches a handler, with per-owner rate limits, a write budget per turn, and input caps, and an unknown tool name is refused outright.
Its behaviour is pinned by a new evaluation suite that drives the real endpoint, loop, guards, tools, and handlers against a scripted model, so tool-calling, RAG grounding, and streaming are regression-tested without a network.
And what it does at runtime is now observable: a Prometheus scrape endpoint and OpenTelemetry traces expose tool latency, error rates, token usage, retrieval confidence, and a span-level trace of which tools ran and why.
Nothing here loosens the earlier stance: the model still reaches the domain only through the same command handlers, a refused call reads to the model like any validation error, and a number the system cannot measure is still reported as unknown rather than as zero.

### Highlights

- Agent sandbox: a `ToolGuardPipeline` runs at the single point where the model's intent becomes execution, so a tool cannot be added past it; guards split `Check` from `Commit`, so a rate-limit token is never spent on a write another guard then refuses (ADR 0035)
- Per-owner rate limits as in-process token buckets — one for tool calls, one for Anthropic round trips, the latter shared by the chat loop and the ticket-summary endpoint, closing the unlimited-summaries gap ADR 0033 left open
- A write budget per chat turn, argument-size caps checked before anything parses tool input, and refusal of unknown tool names; retrievals never count against the write budget, so a spent budget does not silence the model's reads
- Agent evaluation suite: a new `Tests.Evaluation` project drives the assistant end to end against a scripted model, faking only the HTTP transport under the Anthropic client, with scenarios for prompt behaviour, tool-calling, streaming, RAG grounding, and metrics — offline and deterministic
- Observability: a `GET /metrics` Prometheus endpoint and OpenTelemetry traces, fed by one decorator over the metrics sink so Prometheus and the AI dashboard cannot drift; tool calls carry an `error` label rather than a pre-computed rate, and each conversation is a span tree traceable from chat to model turn to individual tool call (ADR 0036)
- Tool-call latency is now persisted and shown per tool on the AI Insights page
- Security: pinned `Microsoft.OpenApi` past GHSA-v5pm-xwqc-g5wc, a high-severity advisory pulled in transitively by Swashbuckle

### Demo Notes

#### Suggested demo flow

1. Sandbox: start the API with a tightened limit and ask the assistant to create two tickets

   ```bash
   AgentSandbox__MaxWritesPerTurn=1 dotnet run --project src/ServiceDeskLite.Api
   ```

   The first `create_ticket` succeeds; the second comes back as an error `tool_result`, and the assistant tells the user which ticket it did not create
2. Observability: `curl http://localhost:5300/metrics` with no API key, then run one assistant conversation and scrape again — tool calls, latencies, token usage, and the `error` label are all populated

   ```bash
   curl -s http://localhost:5300/metrics | grep '^servicedesklite'
   ```
3. Tracing: point `Observability__OtlpEndpoint` at an OTLP collector and watch one conversation appear as an `assistant.chat` span with a child per model turn and per tool call, each tagged with the tool, its outcome, and — on a refusal — the guard and its reason
4. Evaluation: `dotnet test tests/ServiceDeskLite.Tests.Evaluation` runs the whole agent offline, no key and no database required
5. AI Insights: the per-tool table now carries an average-latency column alongside call counts, error rate, and confidence

#### What to pay attention to

- The guard pipeline is enforced by position, not by inheritance: it sits at the one admission point, so a new tool that forgets to opt in is still guarded — unlike a base class a tool may simply not inherit from
- A refused call is not a failure — it returns to the model as an ordinary `is_error` result with the reason, and shows up in the AI dashboard's per-tool error rate like any other error rather than vanishing
- The evaluation suite pins the harness, not the model: it asserts the loop, the guards, the tool dispatch, and the SSE shape, all of which are deterministic; it deliberately does not grade the model's own judgment
- There is no error-rate metric by design — a ratio recorded at record time cannot be re-aggregated across windows, so the counter carries an `error` label and the rate is a query-time division
- Retrieval confidence is recorded only for retrieval and duplicate-check kinds; a routing confidence shares the 0..1 range but measures something else, and blending them would give a histogram no query could trust
- Traces cost almost nothing until an OTLP endpoint is configured — the spans always exist, but without a listener there is nothing to export

### Included scope

- Agent sandbox: `ToolGuardPipeline` with `KnownToolGuard`, `InputSizeGuard`, `WriteBudgetGuard`, and `RateLimitGuard`; per-owner `TokenBucketRegistry` and `ModelTurnLimiter`; `ToolCatalog` as the one list of tools and kinds — ADR 0035, #162
- Agent evaluation suite: `Tests.Evaluation` with a scripted model handler over a faked HTTP transport, a scripted knowledge base, an agent-transcript helper, and prompt/tool-calling/streaming/RAG/metrics scenarios; product fixes for broad adapter exception handling and an error event on a null stop reason — #163
- Observability: `MeterAssistantMetricsSink` decorator, `AssistantInstrumentation` on a BCL `Meter`/`ActivitySource`, Prometheus exporter and opt-in OTLP trace exporter, decision spans in `AssistantChatService`, persisted tool-call duration, an average-latency column on AI Insights — ADR 0036, #164
- Security: direct pin of `Microsoft.OpenApi` 2.7.6 to lift the transitive resolution past GHSA-v5pm-xwqc-g5wc

### Known limitations

- Not intended for production use
- Still no real auth — the owner is a constant demo identity resolved through `ICurrentUser`, so the per-owner limits are effectively global; real authentication swaps only that seam
- Rate limits and write budgets are per API instance and reset on restart; a multi-instance deployment would need a shared store, and the deliberate trade is stated in ADR 0035
- The evaluation suite proves the harness is correct, not that the model is good; measuring the model's judgment needs a live model and a different kind of test
- Metrics are per instance, and the Prometheus exporter package is a pre-release (only a beta is published); the scrape format itself is stable
- Traces are exported only when `Observability:OtlpEndpoint` is configured; without it the spans exist but go nowhere
- Assistant metrics are still never pruned, and reset with the process on the InMemory provider
