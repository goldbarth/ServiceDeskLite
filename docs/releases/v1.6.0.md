# ServiceDeskLite v1.6.0 — Autonomous Ticket Worker

### Summary

Every earlier release built an assistant that waits to be spoken to; 1.6.0 lets it work when nobody is there (roadmap milestone M8, the last one).
A background loop reviews open tickets on a schedule: it asks for missing information, parks the ticket while it waits, proposes solutions grounded in the knowledge base, and refers every high-impact decision to a person.
It is not a second agent — the tool-calling loop was extracted out of the chat endpoint, and the worker and the assistant now run the same loop, the same tools, the same guards and the same command handlers.
Two things differ, and both come from the scope the worker opens per ticket: it audits as `ai-worker` rather than `ai-assistant`, and a review guard holds back the writes a human should have approved.
That guard is the whole feature: a refused call comes back to the model as an ordinary error result telling it to comment instead, so the reasoning reaches a person and the ticket is untouched until that person agrees.

### Highlights

- Autonomous ticket worker: `TicketWorker` owns *when* (interval, oldest-first candidates, one bad ticket never ends the loop), `TicketReviewer` owns *what*; off unless `AutonomousWorker:Enabled` says otherwise (ADR 0037)
- The agentic loop is extracted from `AssistantChatService` into `AgentLoop` + `ToolDispatcher`; the chat endpoint is now an adapter that turns loop events into SSE, and a second loop that would drift from the first was deliberately not written
- `HumanReviewGuard` joins the sandbox pipeline and constrains autonomous runs only: reads always pass, `add_comment` passes because it changes nothing, triaging and parking pass because they sort a ticket without finishing it — everything else is refused with the way out named
- Twelfth tool, `add_comment`: a write on a ticket that changes no state — a follow-up question, a proposed solution, or the reasoning behind an action left for a human to approve
- The audit trail tells the two agents apart: `ai-worker` is a distinct actor, and both count as automated through one shared list, so the EF and InMemory dashboard repositories cannot disagree about what "automated" means
- The worker's authority is validated configuration, not a sentence in a prompt; collections bind into an empty list so a narrower policy replaces the defaults rather than being appended to them
- Seven deterministic worker scenarios join the evaluation suite, alongside guard, options-binding and tool-input tests

### Demo Notes

#### Suggested demo flow

1. Start the API with the worker on and a short interval, against a freshly seeded store

   ```bash
   AutonomousWorker__Enabled=true \
   AutonomousWorker__ScanIntervalSeconds=30 \
   AutonomousWorker__MinTicketAgeMinutes=0 \
   dotnet run --project src/ServiceDeskLite.Api
   ```

   The first log line prints the *effective* policy — an operator narrowing the worker's reach can see in one line whether it took
2. Watch a thin ticket: the worker reads it, finds the missing information, comments a follow-up question, and parks the ticket in `Waiting`. It will not ask again on the next scan, because the review sees the comments it already left
3. Watch a ticket it wants to close: the `change_ticket_status` call is refused, the model reads the refusal, and its proposal lands on the ticket as a comment for a person to approve
4. Open the ticket in the web UI: the comment is authored by the worker, and the audit trail names `ai-worker` rather than `ai-assistant`
5. Widen the policy without touching code — grant it `Resolved` and re-run

   ```bash
   AutonomousWorker__Enabled=true \
   AutonomousWorker__AutonomousStatusTransitions__0=Triaged \
   AutonomousWorker__AutonomousStatusTransitions__1=Waiting \
   AutonomousWorker__AutonomousStatusTransitions__2=Resolved \
   dotnet run --project src/ServiceDeskLite.Api
   ```

6. `dotnet test tests/ServiceDeskLite.Tests.Evaluation` runs the worker offline against a scripted model — no key, no database

#### What to pay attention to

- The refusal is the guardrail, not an error path. The model is told what to do instead and not to retry, and it complies — the outcome the guard exists to produce is a comment, not a failed run
- The worker cannot grant itself its own authority: a scope is the interactive assistant by construction, and `TicketReviewer` throws rather than run in one. The autonomous actor comes into existence in exactly one place
- Two agents, one loop. Every bound the sandbox places on a tool call — rate limits, write budgets, input caps, retries, metrics, spans — applies to the worker because it is the same code, not because someone remembered to apply it twice
- `Waiting` is not scanned, and `Triaged` is autonomous. Both follow from the workflow: the worker parks a ticket it has asked about, and the only transition out of `New` is to `Triaged`, so without it a new ticket would sit in the queue looking actionable while it waited for a reply
- The options binder appends to a non-empty collection. Binding into an empty one and applying defaults afterwards is what makes a configured policy mean what it says — a deployment narrowing the scan to `Resolved` would otherwise have widened it to four statuses
- A guard refusal is recorded like any other error result, so referrals to a human raise the per-tool error rate on the AI dashboard. That is honest — nothing was written — and it is worth knowing before reading the chart

### Included scope

- Autonomous ticket worker: `TicketWorker` (`BackgroundService`), `TicketReviewer`, `AutonomousWorkerOptions` with validated binding and `ValidateOnStart` — ADR 0037, #165
- Agent loop extraction: `Assistant/Agent/` with `AgentLoop`, `ToolDispatcher`, `AgentLoopEvent`; `AssistantChatService` reduced to the SSE adapter and the conversation concerns (transcript, date, timezone)
- `HumanReviewGuard` in the sandbox pipeline, refusing only what an unattended agent should not decide alone
- `add_comment` tool for both agents
- `IAgentActor` / `AgentActorContext`: the audit actor and the review mode come from the scope, not from the tool; `AuditActors.AiWorker` and a shared `Automated` list read by both dashboard repositories
- Tests: `HumanReviewGuardTests`, `AutonomousWorkerOptionsTests`, `AddCommentToolInputTests`, and `AutonomousWorkerTests` — seven scripted worker scenarios covering asking and parking, a refused close becoming a proposal, grounding before posting, auditing as the worker, a vanished ticket, and an upstream failure that ends one review without taking the worker down
- Docs: ADR 0037, runbook section with the full configuration table, README, testing overview, project structure

### Known limitations

- Not intended for production use
- Still no real auth — the owner is a constant demo identity resolved through `ICurrentUser`, so a busy worker and a busy user share one per-owner rate-limit bucket; real authentication at that seam separates them without changing the worker
- The worker is single-instance by construction: two API instances with it enabled would review the same tickets, since candidate selection takes no lease
- A guard refusal counts as an error on the AI dashboard's per-tool error rate, so a healthy worker raises the error rate of the tools it is not allowed to call
- The proposal reaches a person as a comment, not as an approval queue with its own state — accepting or rejecting it is a human action on the ticket, deliberately unmodelled (ADR 0037)
- The evaluation suite proves the harness is correct, not that the model is good; whether the worker asks a *useful* question needs a live model and a different kind of test
- The worker never learns from a rejected proposal; nothing feeds an approved or ignored comment back into a later scan
